## 1. 评审方法

1. 逐份通读需求文档、页面原型说明、四份设计文档、两份规则文档与建表脚本。
2. 以“需求 → 模块 → 数据表 → API → 权限/校验”的链路做覆盖检查，确认每个核心需求都有落点。
3. 对数据库文档与 `schema.sql` 做表、字段、索引、约束和无物理外键的静态比对。
4. 对 API 文档做接口数量、错误码、HTTP 状态、权限矩阵、异步流程、敏感字段过滤和数据库字段映射检查。
5. 对能够明确判断的文档不一致直接修正；涉及业务规则选择的事项不擅自决定，集中列入第 8 节。

## 3. 功能完整性检查

### 3.1 模块与核心流程

- 9 个模块（M01～M09）均有明确的职责、核心数据、依赖、被依赖和页面归属。
- 核心流程 F1～F10 均能映射到模块与 API：
  - 注册登录、CF 绑定/解绑、其他平台申报；
  - 路线/阶段学习与阶段完成；
  - OJ/客观题/简答题提交与判题；
  - 周榜/总榜；
  - 错题本；
  - 1v1 对战；
  - AI 造数据；
  - 运营后台管理与审计。
- 展示聚合层不单独建后端模块，首页、XCPC、导航由现有接口组合，符合“首期不做聚合接口”的决策。
- 后台工作台复用登录信息与操作日志，不新增数据看板，未超出 PRD 范围。

### 3.2 需求到接口覆盖

`04.API接口设计.md` 第 7.4 节已逐项列出 U/H/R/P/L/B/D/G 与 A-01～A-13 的接口覆盖，结论均为“已覆盖”。本次复核未发现核心功能缺少 API 的情况。

需要特别注意的两点：

1. **外链题完成**：当前设计仅支持手动标记，`external_completion.completion_source` 的 `auto` 枚举保留但无写入路径。这与 Q-API-01 一致，但与 PRD 仍保留的“CF 题自动识别”表述不一致，见 V-03。
2. **CF 数据来源**：数据库只有 CF 周过题数/历史累计，没有“某道 CF 题是否 AC”的题目级数据，因此不能实现 PRD 概念上的自动单题完成；该限制已在 01、03、04 中同步说明。

### 3.3 功能边界

- 未新增 PRD 未定义的功能：无随机匹配、观战、回放、人工判分、课程观看进度、自定义角色、管理员改分、造数据取消/重试等。
- 明确不提供的接口已在 `04` 第 7.6 节集中列出，边界清楚。
- 后台角色仍为 `super_admin` / `content_operator` 两类；内容运营只读用户列表/详情，不能新增、启停用、删除用户、重置密码或更换头像，也不能管理管理员账号、不能刷新 CF。

## 4. 架构合理性检查

### 4.1 技术架构

- 前端 Vue 3 + TypeScript + Vite + Element Plus；后端 Java 21 + Spring Boot 3.5 + MyBatis-Plus + Spring Security/Spring Session + Flyway；MySQL 8.4 LTS 为业务事实源；Redis 7.4 只承担会话、限流、锁、可选榜单缓存和临时在线状态；Nginx 同源部署；Docker Compose 单机部署。
- 判题与 LLM 造数据通过数据库任务表 + worker 轮询执行，不引入消息队列；go-judge 作为独立沙箱服务。该选型与首期规模、单机部署约束匹配。
- 本文未更换任何已确定技术栈。

### 4.2 模块边界与依赖

### 4.3 数据事实边界

- MySQL 是账号、题目、提交、首次 AC、榜单来源、对战结果、造数据任务与操作日志的唯一业务事实源。
- Redis 不保存不可重建的业务事实；榜单缓存为可选读优化，失效由首次 AC、申报、CF 刷新、用户状态变化触发。
- 对战状态变更全部走 REST，WebSocket 只做服务端推送与心跳，避免 REST/WS 双写。
- 文件下载只返回二进制，不套统一响应包络；生成器代码无任何下载接口。

## 8. 评审确认结果

### V-01 简答题满分与及格线（已确认 A）

**原问题：** 数据库和 API 原允许 `maxScore` 取 1–100，但判分规则固定 `score>=60` 为通过；当满分小于 60 时，满分作答也无法通过。

**用户确认：** 采用 A——简答题满分固定 100，及格线固定 60；简答题 `maxScore` 只允许 100，评分要点之和必须为 100。

**已同步：**

- `01`：M04 简答题口径与核心数据改为“满分固定 100”。
- `03`：`problem.max_score` 说明、发布校验、`submission` 判分说明与 DB-DEC-11 统一为固定 100。
- `04`：`ADM-PRB-02/04/06`、`SUB-01`、`ScoringRubricItem`、Q-API-06 统一为满分 100、评分要点之和 100。
- `schema.sql`：`problem` 增加 `chk_problem_short_max_score`，约束简答题 `max_score=100`。

**结论：** V-01 已关闭；后续实现不得再支持可变满分。

### V-02 CF 多历史账号的榜单聚合口径（已确认 A）

**原问题：** 同一用户解绑后重新绑定，会保留多条 `external_account`；原文档未定义周榜/总榜应取哪一条，存在重复累计或历史成绩丢失风险。

**用户确认：** 采用 A——每个用户每个平台只取一条记录：优先 `active_flag=1` 的当前有效绑定；没有有效绑定时，取最近解绑的一条历史记录。

**统一口径：**

1. 选定记录：按 `user_id, platform` 分区，排序 `active_flag DESC, unbound_at DESC, id DESC` 取第一条。
2. 周榜：仅当选定记录 `weekly_week_start = 本周周一` 时取 `weekly_count`，否则按 0。
3. 总榜：取选定记录的 `all_time_count`。
4. 重新绑定后旧绑定不再计分；解绑后未重新绑定，保留最近一条历史绑定的累计成绩。
5. 禁止把同一用户同一平台的多条历史绑定相加。

**已同步：** `03` 的 4.2.1 与 7.2、`04` 的 `LB-01` / `ADM-LB-01`。该口径只影响查询，不需要修改 `schema.sql` 表结构。

**结论：** V-02 已关闭；实现时按上述单一记录口径编写榜单查询。

### V-03 PRD 与设计的“外链题自动完成”差异（按建议处理）

**原问题：** PRD 仍保留“CF 外链题自动识别/自动完成”表述；设计因缺少题目级 CF AC 数据源，统一为选手手动标记 + 管理员人工核实。

**后续动作：** 下一版 PRD 将外链题完成统一改为“手动标记”，删除自动识别表述；`external_completion.completion_source` 的 `auto` 枚举继续保留但无写入路径，待未来具备题目级数据源后再启用。

## 9. 已知限制与残余风险

以下事项不属于本次可修正的文档矛盾，但需要在实现或验收时保留意识：

1. **MySQL 版本验证**：增加 V-01 约束前的 `schema.sql` 曾在 MySQL 8.0.34 临时实例验证通过；当前脚本（含 `chk_problem_short_max_score`）尚未在目标 MySQL 8.4 LTS 实机执行，部署前应重新执行验证。
2. **CF 周历史不保留**：数据库只保存当前周快照与历史累计，历史周榜不可追溯；这是已确认的已知限制。
3. **榜单实时派生**：不保存快照，数据量大时查询变慢；首期以索引和分页兜底，后续可加短期缓存或预聚合。
4. **原型角色差异**：已同步修正——原型后台的“刷新 CF 数据”按钮仅超级管理员可见，并补充了对应用例说明，不再保留该项作为待办。
5. **测试数据存储**：`LONGTEXT` 适合演示规模；大数据量需迁移文件存储。
6. **操作日志永久保留**：磁盘增长需要运维监控和归档策略。
7. **无物理外键**：题目、阶段、用户等引用完整性完全依赖应用层；实现时必须把 03 的删除/引用规则落实到 Service 层。
8. **空路线发布**：Q-API-07 已确认不额外校验阶段数量，允许先发布空路线，属于已知产品风险。
9. **简答题可重复提交**：参考答案在提交完成后返回，存在再次提交刷分/套答案的风险；PRD 未定义防刷规则，本期按允许重新提交处理。
10. **对战断线误判**：5 秒心跳、连续 2 次未回 pong 判定的阈值可配置，弱网仍可能误判。
